3サイト共通の記事パイプライン（自動実行モード）。環境変数 SITE_ID が対象サイトを示す。CLAUDE.md の Phase 1〜7 を、対象サイトの設定に合わせて実行し、新規記事を1本作成すること。

【最初に必ず行うこと】
(1) `python scripts/site_brief.py "$SITE_ID"` を実行する。対象サイトのテーマ・読者・担当領域・書いてはいけない領域・カテゴリ・次に書くKWが全て表示される。以降はこの出力に従うこと（自分でサイト設定を探し直さない）。
(2) 表示された「次のKW」をそのまま採用する。表示が空、または need_replenish=true の場合は `python scripts/kw_discover.py --site "$SITE_ID" --append` を実行してから再度 site_brief.py を実行する。
(3) 記事作成の前に `python scripts/cannibal_check.py --cross` を実行し、採用予定のKWが TERRITORY_CHECK や CROSS_CANNIBAL に出ていないことを確認する。出ていた場合はそのKWを使わず、次の候補に移る。
(4) `python scripts/growth_guard.py` を実行する。GROWTH_DROP=yes の場合、**新規記事より先に、落ちた原因を直すこと**。表示が落ちたまま新規を積んでも総量は増えない。消えた語のページが200を返すか確認し、404や配信漏れなら直す。順位が下がった語は `python scripts/cannibal_check.py --serp` で自社ページの食い合いを確認する。
(5) `python scripts/lessons.py --brief "$SITE_ID"` を実行する。**これまでに同じ失敗をした内容が出るので、必ず守ること。**機械の検査で止められるものは載っていない（載っているのは判断が要るものだけ）。
(5b) `python scripts/win_patterns.py --brief "$SITE_ID" --kw "<採用したKW>"` を実行する。AI検索に実際に引用された記事の型（冒頭・見出し・表とFAQの数）が出る。出たら、新しい記事の冒頭と見出しの作りをその型に揃えること。「引用実績はまだありません」と出たら何もしない（無いものを型にしない）。
(6) `python scripts/anchor_audit.py` を実行し、今回書く記事の狙う語が、既存記事からのリンクで指されるようにする。記事を公開したら、関連する既存記事1〜2本から、狙う語を含む自然な一文でリンクを送ること。アンカーが「こちら」やタイトルの丸写しだけだと、その語との結びつきが作られない。

【終わったら学びを残す（次の記事に効かせるため）】
今回つまずいたこと・うまくいったことが **これまでに無い内容** なら、最後に1件だけ積む。
  python scripts/lessons.py --add --kind failure --phase design     --rule "次からこうする（1文・命令形）" --detail "何が起きたか（数字つき）" --source "<slug>"
守ること:
- 既に台帳にある内容は積まない（--brief に出ていたものは既にある）
- 機械の検査で止められるものは、学びではなく検査にする。`--gate "<検査の名前>"` を付けて積み、
  検査が無ければ「検査を作るべき」として --detail に書く
- 1回の実行で2件以上積まない。ためるほど読まれなくなる

【毎月積み上げるための考え方】
表示とクリックは「新規記事の寄与 −（既存記事の下落＋消えたページ）」で決まる。新規を毎日出しても、既存が落ちていれば総量は増えない。だから毎回の実行で、先に落ちを止めてから新規を積む。

落ちる原因は限られている。順に潰す。
  1. ページが検索結果から消えた（404・noindex・配信漏れ） → 最優先。1ページで数百の表示を失う
  2. 自社ページ同士の食い合い → どちらも上がらない。勝たせる側へ内部リンクを集約する
  3. 鮮度切れ（更新から6か月以上） → 数値・事例・時点表記を更新する
  4. 狙う語との結びつきが弱い → 内部リンクのアンカーに狙う語を入れる

【最重要のルール: サイトの担当領域を越えない】
3サイトは同じ会社が運営しており、同じテーマを扱うと検索評価を奪い合う。site_brief.py が表示する「書いてはいけない領域」のテーマは、記事の主題にしてはならない。文脈上どうしても触れる必要がある場合は1〜2文にとどめ、担当サイトへの外部リンクで送ること。

【読みやすさ（機械採点で落ちるので必ず守る）】
- 段落は150字以内。長くなったら意味の切れ目で改行して段落を分ける
- 1文は50字以内。「〜であり、〜のため、〜します」と接続を重ねず、文を切る
- 3〜4文書いたら段落を変える。画面では改行のない塊が「読みにくい」の正体になる
- score_check.py がこの2項目を検査する。超過すると公開できない

【この記事が選ばれる理由を、書く前に決める（採点の3軸）】
公開後に別工程が3軸で採点する（scripts/rubric.py）。書く前にここを決めておく。

1. 一次性 — そこにしか無い情報があるか
   AIが根拠に選ぶのは、他所に無い数字と経験。まとめ直しは引用されない。
   **自社の一次情報（facts）を最低2箇所、うち1つは母数と時期つきで入れる。**
   登録された数字が無ければ、現場の判断・失敗事例・順番の理由を書く。
   公開情報の引き写しだけの記事は、この軸で6点になり足切りになる。

2. 抽出性 — AIが答えとして切り出せる単位になっているか
   冒頭200字・各H2直下の1文結論・定義・比較表・FAQ のどれを切り出しても、
   **それだけで質問への答えになること。**前の段落を読まないと分からない
   書き方をしない。「これ」「それ」で前を指さない。

3. 決定支援 — 読者が次の行動を決められるか
   **条件による分岐を必ず1つ入れる**（「◯◯なら A、△△なら B」）。
   やらない判断の材料（向かない場合・待つべき場合）も書く。
   最後に、今日できる一歩を具体的に書く。

各10点。**1軸でも7点未満なら不合格。**合計24点以上で公開できる。
点数は自分で付けない（別工程が付ける）。ここでは3軸を満たす中身を書くことに集中する。

【執筆】
- 品質は2段構え。**機械で数えられることは score_check.py が判定する**（全PASSが必須）。
  中身の質は、公開後に別工程が上の3軸で採点する。自分で6観点の点数を付ける工程は廃止した
  （書いた本人が付けた点数は、372本すべてが90点以上になり門として働かなかったため）。
  frontmatter の score は機械採点の通過印として残す（90を入れる）。基準はサイトによらず共通。
- カテゴリは site_brief.py が表示した候補から必ず選ぶ（他サイトのカテゴリを使うとビルドが失敗する）。
- **site_brief.py が「次に書くなら: ◯◯」と出している場合、そのカテゴリで書くこと。**
  主力商材に直結するカテゴリが不足すると、表示が増えても相談につながらない。
  実測で、AI集客ラボは主力の aio が21%（狙い45%）まで落ち、
  代わりに ai-marketing が41%（狙い25%）まで膨らんでいた。
  台帳が返した語がそのカテゴリで書けないときは、`python scripts/hub_client.py next <site>`
  をもう一度実行して別の語を取る。書けない理由をログに残してから次へ進むこと。
- 記事Markdownは常に本リポジトリの articles/ に保存する（サイトを問わず1か所に集約し、品質ゲートとカニバリ検査を一元化するため）。
- 一次情報を必ず入れる。特にコーポレートサイトは3,200店舗以上の支援実績が最大の武器なので、具体的な状況・数字・打ち手を書くこと。

【一次情報は「その記事にしかない数字」を優先する】
site_brief.py が出す一次情報のうち、**先頭に出る「当サイトの実測では、『◯◯』は…」**は
その記事の語について自社が実際に測った数字で、ほかのどのサイトも書けない。**これを必ず使う。**

会社の実績（3,200店舗・2020年3月創業）は、どの記事に書いても同じ一文になる。
実測で126本（37%）が同じ「3,200店舗」を載せていた。肩書きとして1回触れるのはよいが、
**それだけでは「その記事にしかない情報」にならない。**

  ○ 「当サイトの実測では、『口コミ 返信 例文 医療』は8.7位に表示されながら、
     96回の表示でクリックが発生しませんでした。検索結果の時点で答えが済む語です」
  × 「弊社は3,200店舗以上を支援してきました」だけで終える

数字は site_brief.py が出したとおりに書く。丸めたり、良く見えるように言い換えたりしない。
出典（自社サイトのSearch Console実測）と時点を必ず添える。
一覧に無い自社数値は書かない。確認できない数値を書いた時点で、記事全体の信頼が落ちる。

【記事の長さは、検索意図から決める（全部同じ長さにしない）】
フロントマターの `depth:` を、狙う語の性質から必ず選ぶ。既定値のまま書かないこと。

  quick    3,000〜4,000字  手順・定義・1つの疑問に答えるもの
                          例:「gbizid 取得方法」「償却資産税 いつ」
  standard 5,000〜6,000字  比較・選び方・業種別の当てはめ
  deep     8,000字以上     網羅ガイド・ピラー記事（クラスターの親）

**実測で、公開338本のうち312本（92%）が5,000〜5,999字に収まっていた。**
`depth` は273本（81%）が standard のまま。全記事が同じ長さに揃うこと自体が
「機械がまとめて作った」という手がかりになる。読者にとっても、
1つの疑問に答えるだけの記事が5,000字あるのは無駄に長い。

- 手順や定義を1つ説明するだけの語なら quick を選び、短く終える。水増ししない
- クラスターの親になる語だけ deep を選ぶ。1サイトで月2〜3本まで

【量産の指紋を作らない（Google スパムポリシー「大量生成コンテンツの悪用」）】
見られるのは「AIか人か」ではなく「順位のための低品質な量産か」。次は公開前に機械が止める
（`python scripts/scaled_guard.py <slug>` で書き終えたら自分で確かめる）。

- 既存記事と本文の25%以上が重なる → 業種や地名を入れ替えただけの同型にしない。
  その業種・地域にしか無い事情（制度の違い・よくある失敗・一次データ）で書き分ける
- 5本以上の記事に出る定型文が本文の8%以上 → 同じ一文を貼らず、この記事の文脈で書く
- 手順・定義を答える語（とは／やり方／手順／方法／書き方…）を depth: standard で書き、
  長さが全記事の中央値±10%に入る → depth: quick にして答えに要る分だけ書く

公開には監修の記録も要る（記録の無い記事は HELD・監修待ちになり、公開されない）。
HELD は品質の不合格ではないので、書き直さないこと。
- 「5,000字に届かないから内容を足す」は禁止。足りないのは字数ではなく主題の選び方

冒頭の書き出しも型を固定しない。実測で34%が「〜とは」で始まっていた。
定義から入るか、読者の状況から入るか、数字から入るかは、語ごとに選ぶ。

【速度規律】
読み込むファイルは CLAUDE.md / lessons.py --brief の出力 / site_brief.py の出力 / 関連する既存記事のみに限定する（kpi_feedback.md は概況の確認だけに使い、全文は読まない）。構成事前審査は1回の思考でまとめて14項目を判定する。6観点採点は1回の応答でまとめて行う。修正は指摘箇所のピンポイント編集のみ（全文書き直し禁止）。

【公開】
- score が90点未満なら公開しない。articles/ に残して次回の救済に回し、理由をログに記録する。
- 90点以上なら `python scripts/publish_flow.py "$SITE_ID" <slug>` を実行する。画像生成・配信・管制塔への記録までまとめて行われる。
- 実行結果の要約を automation/logs/ の本日のログに残す。
