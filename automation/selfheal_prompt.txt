仕組みの自動修復（自動実行モード）。パイプラインを止めている不具合を、その場で直すことがゴールです。

【最初に必ず行うこと】

次の順に実行し、出力をすべて読む。ここで見つかったものだけを直す。自分で問題を探し直さない。

```
python tests/test_gates.py
python scripts/build.py
python scripts/token_check.py
python scripts/daily_audit.py
```

すべて通り、`AUDIT_OK=yes` が出ていれば、何も変更せず「修復不要」とだけログに残して終了する。

【直してよいもの / 直してはいけないもの】

直してよい:
- scripts/ 配下のプログラムの不具合（例外で落ちる、判定を誤る、想定外の入力で止まる）
- tests/ の期待値が実装とずれている場合の、実装側の修正
- articles/ の壊れたフロントマター（読み込めない、必須項目が欠けている）
- .github/workflows/ の記述誤り（YAMLとして読めない、変数名の間違い）

直してはいけない:
- 記事の中身（文章）。品質の直しは救済（retry_prompt）の担当で、ここではやらない
- 品質の基準そのもの。90点未満を通すために基準を下げることは禁止
- 検査を通すためにテストの期待値を書き換えること。実装を直す
- .env や認証情報。権限不足はプログラムでは直せないため、エラーログに残して終える

【直し方の手順】

1. 落ちている箇所を特定する。例外なら追跡表示（traceback）の最下段のファイルと行を見る
2. **なぜ落ちたかを1文で言えるまで読む。** 症状に合わせて例外を握り潰す修正はしない
3. 直す。既存の書き方に合わせる（コメントは「なぜ」だけ、日本語）
4. **同じ不具合を再現するテストを tests/test_gates.py に足す。** これが無い修正は不完全とみなす
5. `python tests/test_gates.py` と `python scripts/build.py` を通す。両方が通るまで次に進まない
6. 直した内容を1行でエラーログに記録する
   `python scripts/hub_client.py error_log fix "<何が壊れていて、どう直したか>"`

【止まったときの扱い】

- 3回直しても同じ検査が落ちる場合は、それ以上さわらない。壊れ方が想定外なので、
  `python scripts/hub_client.py error_log fix "自動修復できませんでした: <検査名> <症状>"` を残して終える
- 判断がつかない場合も同じ。**中途半端に直すより、壊れたまま報告するほうが安全**

【最後に必ず行うこと】

```
python tests/test_gates.py
python scripts/build.py
```

この2つが通らない状態でコミットしない。通らなければ、加えた変更を `git checkout -- <file>` で戻してから終える。
