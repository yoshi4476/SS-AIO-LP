# オウンドメディア自動運用システム

キーワードの選定から、執筆・品質審査・公開・計測・改善までを回す仕組み一式。
**このフォルダには固有の値が入っていません。** `{{ }}` の箇所を埋めて使う。

---

## 何が入っているか

| 場所 | 中身 |
|:--|:--|
| `scripts/` | 本体。記事の生成・審査・公開・計測・レポート |
| `automation/gas/` | 管制塔（Google Apps Script）。台帳・フォーム受付・KPI集計 |
| `.github/workflows/` | 定期実行。毎日の記事公開、週次の最適化、月次レポート |
| `templates/` | 記事HTMLのテンプレート |
| `site/css` `site/js` | サイトの見た目。記事と画像は含まない |
| `sites/sample.json` | サイト設定の見本 |

**含まれないもの**：記事、画像、認証情報、既存サイトのデータ。

---

## 動く仕組み

```
KW台帳（管制塔）
   ↓ 未着手のKWを1件取る
記事を書く
   ↓ 構成の事前審査14項目
   ↓ 機械採点19項目
   ↓ 品質採点 120点満点中114点以上
   ↓ 重複検査（既存記事と似ていないか）
公開
   ↓ 検索エンジンへ通知
   ↓ 内部リンクの整備
   ↓ 管制塔へ記録
計測 → 週次でリライト → 月次レポート
```

**どこかで落ちれば公開されない。** 基準を満たさない記事が出ることはない。

## 立ち上げの手順

所要は、待ち時間を除いて1時間ほど。**クライアント側の権限設定だけは待ちが出る。**

### 1. 置き場所を用意する

```bash
git init
git remote add origin https://github.com/{{GITHUB_OWNER}}/{{HUB_REPO}}.git
pip install -r requirements.txt
npx @google/clasp login          # 次の手順で使う
```

### 2. 管制塔を作る

台帳・問い合わせ・KPIの置き場。**この一式1つにつき管制塔1つ**で、
クライアントごとに別に作る。

| 単位 | 中身 |
|:--|:--|
| このリポジトリ1つ | クライアント1社 |
| 管制塔1つ | そのクライアント専用 |
| 管制塔が持つサイト | そのクライアントの1〜数サイト |

`.env` の `HUB_URL` は1つしか持てない。**共有すると全クライアントの
台帳・問い合わせ・KPIが1冊に混ざり、解約時に切り離せない。**

```bash
python scripts/bootstrap.py --name "会社名" --notify 通知先メール
```

スプレッドシートの作成、コードの配置、デプロイ、11タブの作成、
`.env` への `HUB_URL` / `HUB_SECRET` / `GAS_SCRIPT_ID_HUB` の書き込みまでを行う。
合言葉は自動で作る。**このURLは誰でも叩ける場所に出るため、短い合言葉にすると台帳を書き換えられる。**

そのあと、**画面での作業が1回だけ要る。**

1. 作られたスプレッドシートを開く
2. 拡張機能 → Apps Script
3. 関数の一覧から **`初期設定`** を選んで実行 → 権限を承認

タブの作成・見た目の調整・メール送信の承認・毎朝の集計登録がまとめて終わる。

```bash
python scripts/bootstrap.py --verify        # つながったか確かめる
```

**ここだけ自動にできない。** メール送信とトリガー登録は、本人が画面で
承認したときにしか許可されない。作ったばかりのプロジェクトは、承認前は
外部からの呼び出しをすべて拒否する。

### 3. 認証情報の残りを入れる

`.env.example` を `.env` にコピーして埋める。手順2で埋まった3項目は触らない。

| 項目 | 取り方 | 無いと |
|:--|:--|:--|
| `ANTHROPIC_API_KEY` | Claude のAPIキー | 記事が書けない |
| `SITE_PUSH_TOKEN` | GitHub → Fine-grained token（Contents: Read and write） | 公開できない |
| `GA4_PROPERTY_ID` | GA4 → 管理 → プロパティ設定 | 流入が測れない |
| `RESEND_API_KEY` | Resend | 問い合わせのメールが飛ばない |
| `YOUTUBE_API_KEY` | Google Cloud | 無くても動く（サジェストだけになる） |

Googleのサービスアカウントを作り、鍵を `indexing-service-account.json` として置く。
GA4に「閲覧者」、Search Consoleに「オーナー」で追加する。

**Search Console は必ずオーナーにする。** 制限付きだとインデックス通知が使えず、
記事が検索に載るまで数週間遅れる。

GitHub Actions で定期実行する場合、同じ値をリポジトリの Secrets にも登録する。
**ローカルの `.env` だけ埋めても定期実行は動かない。**

### 4. サイトを登録する

**記入済みのヒアリングシート（Excel）を渡すだけでよい。**

```bash
python scripts/setup_from_sheet.py <記入済みExcel>          # 確認だけ
python scripts/setup_from_sheet.py <記入済みExcel> --write  # 作る
```

次が一度に作られる。

| 作られるもの | 中身 |
|:--|:--|
| `sites/<id>.json` | サイト設定（テーマ・領域・カテゴリ・KWの起点・CTA・会社情報） |
| `docs/kw-<id>.md` | KW計画の置き場 |
| `site-<id>/` | サイトの骨格。トップ・会社概要・問い合わせ・プライバシー・カテゴリ一覧 |
| `setup-memo-<id>.md` | 次にやることの控え |

**記入漏れがあれば作らない。** ドメイン・テーマ・対象読者・扱う語・一次情報が
空だと止まる。キーワードの起点が200通り未満、扱わない領域が空のときは警告を出す。

会社概要ページには、シートのK面（運営者情報）がそのまま入る。
AI検索は運営者の実在性を見るため、ここが薄いと引用されにくい。

設定JSONを手で書きたい場合は `client_add.py --template` も使える。

### 5. キーワードを仕込む

```bash
python scripts/kw_discover.py --site <id> --deep --append
python scripts/kw_status.py
```

**未着手が60件（30日分）以上あること。** 足りなければ `kw_seeds` を増やす。

### 6. 最初の記事を出す

```bash
python scripts/publish_flow.py <id> <slug>
```

3〜5本を手元で確認してから、GitHub Actions の定期実行を有効にする。

## 毎月積み上げるための考え方

表示とクリックはこの式で決まる。

```
今月の表示 ＝ 新規記事の寄与 −（既存記事の下落 ＋ 消えたページ）
```

**新規を毎日出しても、既存が落ちていれば総量は増えない。**
だから毎回の実行で、先に落ちを止めてから新規を積む。記事生成の指示にも
この順序を入れてある。

落ちる原因は限られている。上から順に潰す。

| 順 | 原因 | 見つけ方 | なぜこの順か |
|:--|:--|:--|:--|
| 1 | ページが消えた（404・noindex・配信漏れ） | `growth_guard.py` | **1ページで数百の表示を失う** |
| 2 | 自社ページ同士の食い合い | `cannibal_check.py --serp` | どちらも上がらない |
| 3 | 鮮度切れ（更新から6か月） | 週次の最適化が拾う | 徐々に落ちる |
| 4 | 狙う語との結びつきが弱い | `anchor_audit.py` | 上がりきらない |

**「毎月必ず上がる」は約束できない。** アルゴリズムの更新も季節変動もあり、
順位は自社の外側で決まる部分がある。この仕組みで防げるのは、
自分たちの不注意で落とす分。実際には下落の大半がそれにあたる。

外側の要因で落ちたときも、**原因が外側だと切り分けられること自体に意味がある。**
内側の問題と混同すると、直さなくていいものを直して事態を悪化させる。

## つまずきやすい点

| 症状 | 原因 |
|:--|:--|
| 記事が公開されない | 配信先の権限切れ。`token_check.py` で確認 |
| 「担当領域を越えています」 | `avoid` と `owns` の設計が甘い |
| 「既存記事と重複」 | 業種名だけ変えた同型の記事。切り口を変える |
| KWが枯れる | `kw_seeds` の組み合わせが200通り未満 |
| 順位が上がらない | 公開から1〜3か月は動かない。正常 |
| インデックスされない | Search Console が制限付き |
| GASが `unauthorized` | `HUB_SECRET` の不一致 |
| 問い合わせが来ない | `authorizeMail` の実行漏れ |
| ダッシュボードが空 | `installTriggers` の実行漏れ |

## 設計の考え方

**品質を人の目視に頼らない。** 1日に複数本を出しながら基準を保つには、
機械で判定できる形にしておく必要がある。19項目の機械採点と6観点の
品質採点を通し、90点未満は物理的に公開されない作りにしてある。

**同じ話題を2本出さない。** 検索エンジンがどちらを評価するか決められず、
両方の順位が下がる。公開の入口で類似度を測って止める。

**記事の長さを揃えない。** 全記事が同じ文字数だと、それ自体が量産の痕跡になる。
`depth` で quick / standard / deep を使い分ける。

**一次情報を必ず入れる。** 公開情報の引き写しはAI検索に引用されない。
自社の実績・現場の失敗例・業界の内情のいずれかを、全記事に入れる。
