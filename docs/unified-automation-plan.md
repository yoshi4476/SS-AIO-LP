# 自動化の1本化 設計書

セブンセンシズが持つ3つのWebサイトの記事自動更新を、**1つのエンジン**に統合する。

---

## 1. 現状（調査結果 2026-07-30）

| サイト | リポジトリ | 中身 | 自動化 | テーマ |
|---|---|---|---|---|
| ai.7senses.co.jp（AI集客ラボ） | SS-AIO-LP | 静的HTML + Python | ✅ 5ワークフロー（最新版） | AIO / LLMO / SEO / MEO |
| lp.7senses.co.jp（AI導入補助金） | seven-HPunyou | 静的HTML + Node.js | ✅ 別系統の自動化 | 補助金・IT導入補助金（7本公開済み） |
| www.7senses.co.jp（コーポレート） | SS-CorporateHP | **Next.js 16 + Cloudflare Workers** | ❌ なし | 未定 |

### 1本化すべき理由

**① 仕組みが二重管理になっている**
SS-AIO-LP（Python）と seven-HPunyou（Node.js）は、やっていることはほぼ同じなのに実装が別物。
品質ゲートの基準も、KW管理も、通知も、それぞれ別に直す必要がある。実際、
seven-HPunyou のpush競合バグは同じ対策を2回書くことになった。

**② サイトをまたいだ共食い（カニバリ）を誰も見ていない**
現在のカニバリ検査は「同じリポジトリ内の記事どうし」しか比較しない。
3サイトとも同じ会社・近い領域なので、**別サイトどうしで同じKWを狙うと共倒れする**。
例:「AI 補助金 集客」を補助金サイトとAI集客ラボの両方が書くと、Googleはどちらも評価しにくくなる。
1本化して初めて、全サイト横断の重複チェックができる。

**③ 運用の窓口が3つに分かれている**
認証トークンの更新、KW設計、レポート確認が3か所。1年後のトークン失効時に3リポジトリを直す必要がある。

## 2. 統合後の構成

**SS-AIO-LP を「自動化エンジン」に格上げし、3サイトへ記事を配信する。**

```
SS-AIO-LP（自動化エンジン）
├── sites/                        ← サイトごとの設定（ここを増やせばサイトが増える）
│   ├── ai-lab.json               ai.7senses.co.jp   / 静的HTML / 自リポジトリ
│   ├── subsidy.json              lp.7senses.co.jp   / 静的HTML / seven-HPunyou へpush
│   └── corporate.json            www.7senses.co.jp  / Next.js  / SS-CorporateHP へpush
├── scripts/                      ← 全サイト共通の頭脳
│   ├── kw_status.py              KW残数（サイト横断で重複除外）
│   ├── kw_discover.py            実データKW発掘（GSC + サジェスト）
│   ├── cannibal_check.py         ★全サイト横断の重複検査に拡張
│   ├── score_check.py            機械採点18項目
│   ├── make_images.py            画像生成
│   ├── publish.py                ★サイト種別に応じた公開処理（新規）
│   └── notify_*.py / monthly_report.py
└── .github/workflows/
    └── pipeline.yml              ★サイトを順に回して1本ずつ生成（1つのワークフロー）
```

### 各サイトの公開方法の違いを publish.py が吸収する

| サイト | 記事の置き場所 | 公開の仕方 |
|---|---|---|
| ai-lab | `articles/*.md` → `site/{cat}/{slug}/index.html` | build.py でHTML生成 → wrangler deploy |
| subsidy | seven-HPunyou の `blog-system/content/posted/` | 対象リポジトリへpush → 既存ビルドが動く |
| corporate | SS-CorporateHP の `src/content/blog/*.json` | 対象リポジトリへpush → CloudflareのGit連携が自動ビルド |

エンジンは「記事Markdownを作って品質ゲートを通す」までを共通で行い、
**最後の出力形式だけをサイトごとに切り替える**。

## 2.5 GAS（Google Apps Script）を統合ハブにする

**スプレッドシート1冊 = 3サイトの管制塔**にする。人間が見る場所と、機械が読み書きする場所を1つにまとめる。

```
┌──────────────────────────────────────────┐
│  Googleスプレッドシート（管制塔）          │  ← 人はここだけ見る
│  ・問い合わせ台帳（3サイト共通・サイト列で区別）│
│  ・KPIダッシュボード（3サイト分を毎日自動更新） │
│  ・KW管理台帳（3サイト分。共食い防止の要）     │
│  ・記事作成ログ / エラーログ                 │
└──────────────┬───────────────────────────┘
               │ GAS Web App（API）
       ┌───────┴────────┐
       │                │
┌──────▼──────┐  ┌──────▼───────────────────┐
│ 3サイトの     │  │ GitHub Actions（記事工場）  │
│ お問い合わせ   │  │ KWを読む → 生成 → 結果を書く │
│ フォーム      │  └──────────────────────────┘
└─────────────┘
```

### GASで統合する利点

**サービスアカウントが不要になる。** GASは実行者のGoogleアカウント権限で動くため、
GA4もSearch ConsoleもJSONキーなしで読めます（現在は `indexing-service-account.json` を
各リポジトリのSecretsに配る必要がある）。鍵の配布・失効管理が消えます。

**KWの重複が人の目で見える。** 3サイト分のKWが1枚のシートに並ぶので、
「このKWはもう補助金サイトが狙っている」が一目で分かります。機械の重複検査と二重の防御になります。

**問い合わせが1か所に集まる。** どのサイトから来た相談も同じ台帳に入り、サイト列で区別されます。
対応状況の管理も1枚で済みます。

**トリガーがGoogle側にある。** 日次のKPI集計はGASの時間主導型トリガーで動くので、
GitHub Actionsの実行時間を消費しません。

### GASが担当する範囲 / GitHub Actionsが担当する範囲

| 処理 | 担当 | 理由 |
|---|---|---|
| 問い合わせ受付・台帳記録・Gmail通知 | **GAS** | 既に `automation/gas/contact.gs` として実装済み。3サイト共通化する |
| GA4/GSCのKPI日次集計 → ダッシュボード | **GAS** | 認証が最も簡単。Actions時間を使わない |
| KW台帳の提供（次に書くKWを返す） | **GAS** | 人が編集できる場所にKWを置けるため |
| 記事の生成・採点・画像・公開 | **Actions** | Claude実行とgit操作が必要 |
| 月次レポートPDF | **Actions** | Playwrightが必要（GASでは不可） |
| 全サイト横断のカニバリ検査 | **Actions** | 記事本文の解析が必要 |

### 実装するGASファイル

- `automation/gas/contact.gs` — 問い合わせ受付（実装済み・3サイト対応に拡張）
- `automation/gas/kpi.gs` — GA4/GSCから3サイト分のKPIを取得しダッシュボード更新（日次トリガー）
- `automation/gas/kw_api.gs` — KW台帳の読み書きAPI（Actionsが叩く）
- `automation/gas/setup.gs` — スプレッドシートの11タブを自動生成（初回1回だけ実行）

## 3. コーポレートサイト（Next.js）に必要な追加実装

他2サイトは静的HTMLだが、SS-CorporateHP は Next.js 16 のため記事表示の仕組みがない。以下を新規に作る。

- `src/content/blog/*.json` — エンジンが書き出す記事データ（本文HTML込み）
- `src/lib/blog.ts` — 記事の読み込み（既存 `news.ts` と同じ作法）
- `src/app/blog/page.tsx` — 記事一覧
- `src/app/blog/[slug]/page.tsx` — 記事詳細（既存 `news/[slug]/page.tsx` の構造を踏襲）
- `src/app/sitemap.ts` に記事URLを追加
- 記事本文用のスタイル（Tailwind のプロース設定 or 専用CSS）

MarkdownからHTMLへの変換は**エンジン側のPythonで行う**（既存の変換処理と装飾ルールをそのまま使えるため）。
Next.js側は出来上がったHTMLを表示するだけにする。新しいnpmパッケージは追加しない。

## 4. 最重要の決定事項: コーポレートサイトのテーマ

AIO・SEO・MEOは **ai.7senses.co.jp** が、補助金は **lp.7senses.co.jp** が既に押さえている。
**www.7senses.co.jp が同じテーマを書くと3サイトで共食いする。**

重ならず、かつ会社の強みが出るテーマの候補:

| 候補 | 内容 | 相性 |
|---|---|---|
| **店舗経営（集客以外）** | 人材採用・定着、スタッフ教育、オペレーション改善、店舗DX | ◎ G-ranの顧客層と一致し、集客記事から自然に送客できる |
| **業種別の導入事例・実績** | 3,200店舗の支援で得た事例を業種別に紹介 | ◎ E-E-A-Tが最も強く出る。指名検索を作れる |
| **経営者向けAI活用（集客以外）** | 経理・労務・顧客対応・資料作成の自動化 | ○ ただしAI集客ラボと境界が近く、線引きが必要 |
| 採用ブランディング | 働き方・社員紹介・企業文化 | △ 集客支援の受注には直結しにくい |

**推奨は「店舗経営（集客以外）＋ 業種別事例」の組み合わせ。**
集客の入口はAI集客ラボ、補助金は補助金LP、**経営全般とその実績はコーポレート**という役割分担になり、
3サイトが競合せず相互に送客できる。
