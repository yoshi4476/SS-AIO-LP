# 認証情報の更新手順

**`secrets.local.txt` に書いて1回実行すれば、`.env` と GitHub Secrets の両方に入ります。**

片方だけ更新すると、手元では通るのにCIで落ちる（またはその逆）が起きます。実際 `SITE_PUSH_TOKEN` はそれで長く401のままでした。

---

## 手順（全体）

```bash
python scripts/set_secrets.py --init     # 1. 雛形を作る
# 2. secrets.local.txt に値を書く（下の発行手順を参照）
python scripts/set_secrets.py            # 3. 中身を確認（まだ書き込まない）
python scripts/set_secrets.py --apply    # 4. .env と Secrets に反映
python scripts/set_secrets.py --clean    # 5. 控えを消す
```

`--apply` の前に `gh auth login` が必要です。まだなら次を実行してください。

```bash
gh auth login
# → GitHub.com / HTTPS / Login with a web browser を選ぶ
```

**`secrets.local.txt` は `.gitignore` 済み**なので、誤ってコミットされません。

## 1. 配信用トークン（最優先・いま401で止まっているもの）

**これが無いと、コーポレートと補助金サイトへ記事を配信できません。** 現在60本が未配信です。

### 発行URL

**https://github.com/settings/personal-access-tokens/new**

### 入力する内容

| 項目 | 値 |
|:--|:--|
| Token name | `SS-AIO 配信用` |
| Expiration | **1 year**（無期限は選ばない） |
| Repository access | **Only select repositories** |

**Select repositories で次の3つを選びます。**

```
yoshi4476/SS-AIO-LP
yoshi4476/SS-CorporateHP
yoshi4476/seven-HPunyou
```

**Permissions → Repository permissions** で次を設定します。

| 権限 | 設定 | 理由 |
|:--|:--|:--|
| **Contents** | **Read and write** | 記事ファイルを書き込むため（**必須**） |
| Workflows | Read and write | 配信先のビルドを動かすため |
| Metadata | Read-only（自動で付く） | — |

**それ以外は「No access」のままで構いません。**

### 注意点

- 発行後に表示される `github_pat_` で始まる文字列を**その場でコピー**してください。画面を閉じると二度と見られません
- 古いトークン（`ghp_` で始まる40文字）は**新しいものが通ることを確認してから**削除してください
  - 削除画面: https://github.com/settings/tokens

### 書き込む場所

```
SITE_PUSH_TOKEN=github_pat_ここに貼る
```

## 反映後の確認

`--apply` を実行すると、自動で `token_check.py` が走ります。次が出れば成功です。

```
トークンの持ち主: yoshi4476
  OK       corporate  yoshi4476/SS-CorporateHP（書き込み可）
  OK       subsidy    yoshi4476/seven-HPunyou（書き込み可）

TOKEN_OK=yes（配信先すべてに書き込めます）
```

**失敗したときの読み方**

| 表示 | 意味 | 対処 |
|:--|:--|:--|
| `トークンが通りません（401 Bad credentials）` | トークンが無効 | 発行し直す |
| `権限不足（読めるが書けません）` | Contents が Read-only | 権限を Read and write に変える |
| `トークンの問題ではありません` | GitHub側の障害 | **再発行しても直りません。**時間をおく |

## 更新後にやること

トークンが通ったら、未配信の記事を配信します。

```bash
# まず対象を確認する（配信はしない）
python scripts/publish_changed.py --all

# この会話で加筆した分だけを配信する
python scripts/publish_changed.py --site corporate --since HEAD~12 --push
python scripts/publish_changed.py --site subsidy   --since HEAD~12 --push

# 全記事を配信し直す場合（本数が多いので --limit で刻める）
python scripts/publish_changed.py --all --push --limit 20
```

**認証で落ちた場合は、その場で中断します。**以降も同じ結果になるため、
何十本も失敗を繰り返さない作りにしてあります。

## 配信トークンが「書き込み可」と出るのに403で落ちるとき

### 何が起きていたか

`token_check.py` は GitHub API の `permissions.push` を見ていた。
これは**そのリポジトリでの利用者（あなた）の権限**であって、
**トークンの権限ではない**。細粒度PATが Contents: Read only でも
`true` が返るため、検査は通るのに配信で 403 になる。

2026年9月6日、この誤判定で補助金サイトへの記事配信が止まった。
検査は「OK 書き込み可」と表示していた。

### 直したこと

`token_check.py` は実際に書き込みを試すようにした。存在しないSHAで
参照を作ろうとし、権限があれば422（内容が不正）、無ければ403が返る。
参照は作られないのでリポジトリには何も残らない。

### 権限が足りないときの直し方

1. https://github.com/settings/personal-access-tokens を開く
2. 該当のトークンを選ぶ（Fine-grained personal access tokens）
3. **Repository access** に次の3つが入っているか確認する
   - `yoshi4476/SS-AIO-LP`
   - `yoshi4476/SS-CorporateHP`
   - `yoshi4476/seven-HPunyou`
4. **Repository permissions** を次のとおりにする
   | 項目 | 設定 | 用途 |
   |:--|:--|:--|
   | **Contents** | **Read and write** | 記事の配信（これが無いと403） |
   | Workflows | Read and write | 自動実行の定義を更新する場合 |
   | Secrets | Read and write | `set_secrets.py` で Secrets を更新する場合 |
5. **Update token** を押す
6. 手元とCIの両方を更新する（片方だけだと結果が食い違う）
   ```
   python scripts/set_secrets.py --apply
   ```
7. 確認する。ここで `TOKEN_OK=yes` が出れば完了
   ```
   python scripts/token_check.py
   ```

### 権限が無いあいだ何が起きるか

`publish.py` はトークンで押せないと、手元のGit認証に切り替えて配信を続ける。
そのため手元では記事が出るが、**CI（毎日の自動実行）は手元の認証を持たない
ため止まる**。放置すると記事が積まれなくなる。
