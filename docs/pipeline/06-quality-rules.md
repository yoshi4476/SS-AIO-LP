## 6. 品質ルール

### AI感排除7項目（全記事必須チェック）

| # | チェック項目 | NG例 | OK例 |
|:--|:--|:--|:--|
| 1 | あいまいな結論 | 「場合もあります」「可能性があります」 | 具体的シナリオ・条件を明示 |
| 2 | 重要ですの連発 | 「〜することが重要です」4回以上 | 記事中3回まで。具体的アクション提示 |
| 3 | 文末パターン同一 | 全段落「〜です。」 | 「です/ます/でしょう/体言止め」交互 |
| 4 | 3連続箇条書き | 箇条書き×3連続 | 間にリード文やテーブル |
| 5 | これにより | 「これにより効率が向上します」 | 完全削除。具体的因果を文章で |
| 6 | おすすめします | 「検討することをおすすめします」 | 「してください」「試してみてください」 |
| 7 | 一人称の欠如 | 第三者視点のみ | 一人称2箇所以上。体験は登録した体験（`data/experiences.json`・お客様の社は非公開の `experiences.json`）からだけ書き、無ければ当社の判断とその理由を一人称で書く |

**AIっぽい言い回しは機械が見つけて直す**（2026-10-20 運用者の決定。`scripts/ai_writing.py`・textlint）。誇張（完璧な・完全に・大幅に）・
「〜することができます」・箇条書きの「**札**:」などを検出し、意味の変わらない直し（誤用の辞書・文字の正規化）は機械が当て、
判断の要るものは指摘の文だけを AI が言い換える（`auto_rewrite --kind aiwriting`。既存の検算＋指摘が減った・ほかの行と「」の引用を変えない）。
新しい記事は公開前の品質ループが採点の前に、公開済みは週次が指摘の多い記事から社ごとに週4本（`ai_writing_weekly`）。
本サイトの書式とぶつかるルール（質問形の H2・1文100字・固有名詞の漢字の連続など）は止めた（理由は `automation/textlint/RULES.txt`）。

| 6 | FAQ 5問以上 | 回答40-60字。本文とSchema完全一致 |

### 装飾ルール（可読性 — 自動生成記事にも必須適用）

記事Markdownで使える装飾。CSSとbuild.pyが自動でスタイル適用する。

| 記法 | 表示 | 使いどころ |
|:--|:--|:--|
| `**テキスト**` | 黄色マーカー+太字 | 核心フレーズ・数値（1記事12-18箇所） |
| `==テキスト==` | 黄色マーカー（太字なし） | 補助的な強調 |
| `*テキスト*` | 青太字+青点線下線 | 用語・キーワードの強調 |
| `<span class="txt-red">` | 赤太字 | 警告・NG事項（1記事1-3箇所まで） |
| `<span class="txt-blue">` | 青太字 | ポジティブな強調 |
| `<span class="big">` | 1.3倍サイズ太字 | 最重要メッセージ（1記事1箇所まで） |
| H2直下の段落 | 自動で紺色太字・大きめ表示 | 1文結論（書くだけで自動強調） |

- 冒頭の断言段落は自動でリード表示（1.13倍）になる
- 装飾の乱用禁止: マーカーは1画面に2-3箇所が目安。全部を強調すると何も強調されない
- マーカー適用範囲: 記事本文に加え、LP・固定ページの `**太字**`/`<strong>` も自動で黄マーカーになる（ダーク背景・CTA・表ヘッダーは除外）。固定ページの重要文言にも `<strong>` を使うこと
- **生HTMLブロックの中では `**` が効かない**: 注意ボックス（`<div class="caution-box">`）など、行頭が `<` のブロックの中は Markdown が処理しない。`**罰金**` と書くと記事に `**` がそのまま出る（実測282箇所）。ボックスの中は `<strong>` を使う
- **表・箇条書き・番号リストの前には空行を1つ入れる**: 空行がないと前の段落の続きとして扱われ、表がパイプ記号のまま本文に出る（実測62箇所）。`scripts/fix_block_breaks.py` が週次で検出・修復する

### 文章ルール

- 文体: ですます調で統一（「だ/である/〜した」調禁止）
- 1文50文字以下 / 段落3行 or 150字以内 / 文長バリエーション / 体言止め2-3箇所
- H2/H3直後: 必ずリード文1-3行（いきなり表・リスト禁止）。H2直後の1行目は1文結論
- H4見出し: サブステップには `<strong>` ではなくH4タグ
- プロンプト表示はコードブロック形式

### 記事構成共通ルール

- 目次: `scripts/build.py` がH2/H3から自動生成（本文Markdownに手動挿入しない）
- テキスト強調: `<strong>` 12-18箇所（核心フレーズ・数値・アクション喚起に限定）
- CTA: 最低2箇所。中央揃えボタンブロック統一
- 「この記事でわかること」ボックスを冒頭に必ず設置
- FAQ 5問以上+FAQPage Schema
- **CV導線の強化**: ゼロクリック前提で「引用でブランド認知→指名検索→CV」導線として設計。社名・サービス名を数値ファクトとセットで記述し、AI回答内に社名ごと引用される形を狙う

### 画像ルール（本サイトの運用実装）

自動生成でも以下を必ず実行する（画像生成API未設定時のフォールバックツールを用意済み）:

1. **アイキャッチ必須**: 全記事のフロントマターに `eyecatch:` を設定する。生成は **`python scripts/make_images.py <slug>`（推奨・一括）** — フロントマターのtitle/categoryからアイキャッチを自動生成し、`diagrams:` 宣言があれば図解も一括生成する。タイトルは自動折り返し・自動縮小のためはみ出しなし。PNGは自動軽量化される。個別生成は `make_eyecatch.py <slug>` でも可
2. **一覧サムネイル自動**: build.pyがアイキャッチを記事一覧・関連記事のサムネイルとして自動表示（eyecatch未設定時はカテゴリ色のグラデーションにフォールバック）
3. **本文図解**: 手順・構造系のH2には図解を入れる。記事フロントマターに `diagrams:` を宣言して `make_images.py <slug>` で一括生成（推奨）。型は3種: `flow`（手順2〜5）/ `list`（チェックリスト3〜6項目）/ `vs`（NG・OK比較2カラム）。個別生成: `python scripts/make_diagram.py [--type flow|list|vs] <slug> <ファイル名> <タイトル> <項目...>`。テキストは自動縮小されはみ出さない。build.pyが画像の生成漏れを機械検出する
4. **文字化け検証**: 画像生成後は必ずReadで目視確認。日本語が欠け・化けた場合はフォント（YuGothB/meiryob）の存在を確認して再生成
5. **実写素材**: `site/images/company/` の自社素材（ロゴ・代表写真・G-ran資料画像）を優先使用。外部素材は権利確認済みのもの以外使用禁止
6. **ロゴ**: ヘッダー=`logo.png`、フッター/ダーク面=`logo-white.png`、アイコン=`star-white.png`（七の文字ロゴは廃止）

### 画像ルール（一般原則）

- アイキャッチ: フラットイラスト・16:9・カテゴリカラー準拠
- H2直下図解: フラットベクターイラスト、テキストなし or 日本語のみ
- **英語テキスト絶対NG**（プロンプトに「No English text」必須）
- altテキスト必須（KW詰め込みNG）
- 生成後の目視チェック必須。画像依存禁止（AIO/LLMOルール12）

### 機械品質ゲート（build.pyが自動検査 — 警告ゼロが公開条件）

| 検査 | 基準 | 実装 |
|:--|:--|:--|
| タイトル字数 | 15〜45字 | build.py quality_checks |
| メタ記述字数 | 100〜160字（目安100〜150字。Bing の「短すぎる」指摘に合わせた 2026-10-05） | 同上 |
| カニバリ防止 | タイトル類似80%以上でWARN（差別化 or 統合） | 同上（KW選定段階の機械スキップと二重防御） |
| 内部リンク404 | 全内部リンクの存在検証（404ゼロ保証） | build.py link_check |
| マーカー数 | 強調8箇所以上（推奨12-18） | build.py（記事ごと） |
| 文字数 | 本文5,000字以上（タグ・空白除く実文字数） | build.py（記事ごと） |
| 鮮度・通知 | sitemap lastmod自動 + `notify_indexnow.py` / `notify_indexing.py` で**3サイトとも**即時通知 | Phase 7 / 週次リライト後 |
| **描画の崩れ** | 生成HTMLに生のMarkdown記法・空リンク・alt無し画像が残っていない | `scripts/render_check.py`（build.py が自動で呼ぶ） |
| **取りこぼし** | 原稿にある表・リスト・見出し・画像・リンクが、出力に同じ数だけ出ている | `render_check.structure_gap()`（build.py が自動で呼ぶ） |
| **サイト監査（Ahrefs 相当）** | 記事以外も含む全ページで: sitemap の404/noindex/転送・題と説明の欠け長さ重複・OGP・H1・alt・構造化データ・http混在・孤立・重い画像。致命的と警告はゼロ | `scripts/seo_audit.py`（build.py が WARN、ゲート `test_site_audit_has_no_critical_or_warning` が止める。週次は3サイトの本番を外部リンク切れ・別ドメインへの転送まで巡回） |
| **衝突マーカー** | 原稿に `<<<<<<<` / `=======` / `>>>>>>>` が無い（`=======` の直前の行が H1 として公開される） | ゲートと publish.py が止める（2026-09-29 に17本が公開されていた） |
| **入れてはいけない HTML・外への転送** | 本文・題・説明・FAQ に ld+json 以外の script・on 属性・iframe・外部への form・javascript: が無い。`site/_redirects` の転送先は内部のパスと自社のドメインだけ（AI は外の文章を読むので、仕込まれた指示で入れられうる）。地図・動画は原稿の1行の記号 `@[地図](住所)`・`@[動画](11文字の id)`（各3つまで）から機械が決まった形で作り（HTML の形式は iframe・WordPress と先方変換の Markdown はリンク）、記号から作った iframe だけを通す | `scripts/html_safety.py`（build.py・publish.py の全形式と --check・seo_audit --gate・score_check。2026-10-11）・`scripts/embeds.py`（2026-10-12） |

**症状の一覧では足りない理由**: 上の描画検査は「こちらが知っている壊れ方」しか見つけられない。実際、4種類の崩れが長期間だれにも気づかれずに公開されていた。そこで**中身を見ず、原稿と出力で塊の数だけを突き合わせる**検査を足した。知らない壊れ方でも、変換に失敗すれば数は合わなくなる。

**原稿ではなく出力を見る検査がある理由**: 上の他の検査は全部、原稿（Markdown）だけを見ている。そのため「原稿としては正しいが、変換すると壊れる」崩れが素通りしていた。実際に見逃したもの — 表がパイプ記号のまま本文に出る（62箇所）・`**` がそのまま表示される（282箇所）・`[文字](/url/)` が押せない形で出る（34箇所）・段落が装飾の内側で分かれて `**` が次の段落へ残る（19箇所）。**どれも記事の点数には出ず、読者の画面にだけ出る。**

### 公開条件（85点未満はアップロード不可 — build.pyが物理的に強制）

1. Phase 5の3観点採点（各100点）の**平均**を、記事フロントマターの `score:` に記録する（換算式: `round(3観点の合計/3)`）。**1観点でも80点未満なら、総合が足りていても不合格**。
   今の運用では、記事を書く AI は点数を書かず、公開前の別工程の採点（`quality_loop.py`）が基準に届いたときだけ機械が `score` を書く
   （Phase 5 の「今の運用」）。`quality_state: improving` の記事は点数があっても公開しない。
   機械の手順は配信の前にこの回の新しい記事へもう一度 `score_check` を当て、落ちた記事は `articles/_conflicted/` へ移す（`agent_guard.py --publish`。公開済みの記事は動かさない）。
   採点の台帳に合格の記録が無い新しい記事も配らず、改善中にして次の回へ回す
2. **`score` が85点未満、または未記載の記事は build.py がビルド対象から除外**する（サイト・sitemap・feed・一覧のどこにも掲載されない = アップロード不可）
3. build.pyの機械品質ゲートで警告ゼロ（メタ字数・カニバリ・リンク404・マーカー数）
4. 未達は修正ループ（`quality_loop.py`。1回の実行で2回まで直して採点し直す）→ なお未達は改善中のまま次の回が直し続け、3日を超えたら週次の findings が要対応で知らせる
- **厳しさの調整（2026-10-21 運用者「かなりではなく少し厳しいに」「緩和しても AI から選ばれるように」）**: 一次性は80点のまま（AI が根拠に選ぶ独自の情報）、抽出性と決定支援は75点に下げた。2回採点したときは軸ごとに平均を採る（低い方を採ると採点の揺れの下振れだけで落ちた）。書く段階の採点の観点の検査（前を指す文・決定支援・抽出の単位・仮の計算例）は警告にし、止めずに直しの指示へ名指しで渡す
- 公開の下限は85点、目標は90点、推奨水準は95点以上（2026-10-21 運用者「100点満点中85までで通すようにしよう」。基準は `rubric.PASS_TOTAL`・`rubric.TARGET` の1か所だけ）
- **PDCA を常に回す**（運用者「改善できるようにPDCAを常に回すこと」）: 公開前の品質ループは85点に届いても90点未満なら回数の残りで直し続け、点が下がった版は捨てる。85〜89点で公開した記事は「直す対象」に残り、毎日の記事の枠（`quality_loop --rescore-auto`）と週次（`--rescore`）が採点 → 直し → 採点し直しを90点に届くまで続ける。採点の弱点は台帳（`data/quality_loop.jsonl`）に残り、何度も出る弱点は書く段階の検査（`score_check`）と指示に足していく
