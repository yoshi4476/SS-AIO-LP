## 4. 自動化パイプライン定義（全7Phase）

各Phaseの完了を確認してから次に進むこと。

### Phase 1: KW選定エージェント

**目的**: 次に書く記事のキーワードを決定する。

-1. **在庫の作り方（2026-10-09 運用者の決定: 書く記事が1か月分を切ったら、その社だけ。月の途中でもよい）**
   ```bash
   python scripts/kw_plan.py --site <id> --dry-run   # 課金なし。候補の構成と目的ごとの見積もり（docs/kw-plan-<id>.dry.md）
   python scripts/kw_plan.py --all --if-needed       # 1か月分を切った社だけ積み足す（毎日の見張りが呼ぶ）
   python scripts/kw_plan.py --site <id> --replace   # 一新（古い未着手を対象外にして積み直す。手で使う）
   python scripts/kw_plan.py --site <id> --main-first 20   # 主力の語だけを優先度Aで積み足す（今の未着手は消さない。手で使う）
   python scripts/kw_serp.py --brief <id> --kw "<語>" # 取った上位ページの見出し・共起語・質問（執筆の 5c が読む）
   ```
   毎日の在庫の見張り（`daily-kpi.yml` の `kw-stock` ジョブ）が、台帳の未着手が**1か月分（1日の本数×30・月の上限60まで。
   量産の兆候で本数を絞った社は絞った本数で）を切った社だけ**、その日に `kw_plan --all --if-needed` で積み足す。
   **1社1か月1回**（組んだ月を `data/kw_plan_runs.json` に社のIDと年月だけ残す。台帳に積めなかった回は残さず翌日やり直す）。
   積むのは**1か月分×1.2 まで**（今の未着手は触らない）。流れは成果に近いものから:

   | 順 | 工程 | 課金 | 中身 |
   |:--|:--|:--|:--|
   | 1 | 候補 | なし | **検索の実績で4〜30位・表示10回以上なのに狙う記事が無い語（需要と届く見込みが実証済み）を最優先**。続けてシートの狙う語・`kw_seeds` の主力×業種・Google の無料サジェスト・AI検索の質問形（`ai_kw`）・30日以内のラッコの控え |
   | 2 | ふるい | なし | `kw_fit`・食い合い（`kw_guard` と同じ GSC の実績）・既存の除外・台帳（同じ組のどの状態の語も）と記事との重複。**実証済みの語のうち既存記事が順位を持つものは新しく書かず、その記事の書き直しへ回す**（新記事は食い合う）。記事以外のページ（トップ・カテゴリ一覧・LP）が持つ語は `kw_guard` が着手禁止にするので積まず、計画に書く |
   | 3 | 検索数 | 一括検索数 30 | 上位の候補で検索数の無いものだけ一括調査1回（SEO難易度は付けない） |
   | 4 | 並べる | なし | 点（下記）＋**実証済みの語に +5**。**主力の語の割合を主力の配分以上に保つ**（補助金は `scheme_mix` の一番大きい制度、ほかは `category_mix` の `main_category`）。**問い合わせに近い根拠の無い語（検索数だけ）は積まない**。同じ主題の束では**個別の記事を先・まとめ（ピラー）を後**。語ごとの出どころ（gsc/sheet/seed/question/suggest/cache/rakko）を計画・台帳の備考・`data/kw_origin.json` に残す |
   | 5 | 見出し・共起語 | 見出し・共起語 70 | これから書く優先度Aの上位（目安10語）と、4〜20位の自社記事の狙う語を交互に → `data/kw_serp/<id>.json`（見出しは40字まで・出現数・共起語だけ。相手の URL・題・本文は残さない。ラッコの規約は社内利用なので**自社の分も Git に入れず**、client_private の置き場＝CI のキャッシュで渡す）。執筆の指示（5c）と書き直し（`auto_rewrite` の stuck・compete）が読む |
   | 6 | 実際の質問 | 実際の質問 30 | 上位の約20語 → 執筆の FAQ の候補（**答えは記事の事実だけで書く**） |
   | 7 | 予備 | 予備 20 | 無料の候補が足りないときだけ、ラッコのサジェスト・関連語 |

   点は「外注・比較を考えている語（+3）／開く理由／検索数（対数×0.6）／
   難易度の低さ／12か月の伸び／自サイトの表示実績／実証済み（+5）」の合計。**検索数だけで並べると、
   「請求書 封筒 書き方」（自分でやる人）が「経理代行 費用 相場」（外注を考える人）の
   上に来る。** 目的はリードなので買い手の語を先に置く。

   **狙う業種の優先度**は `kw_seeds.priority` で指定する。優先業種は枠が厚く（20本／他は10本）、
   点にも加点される（+1.5）。AI集客ラボは「クリニック・歯科医院・不動産・リフォーム・工務店」
   （月1件の成約で集客支援の費用が回収できる業種）、補助金は「個人事業主（売上の大きい層）・
   中小企業全般」。他業種の起点も残し、汎用性は捨てない。読者像（`audience`）も同じ方針で書く
   — 執筆側がこれを読んで記事の想定読者を決める。

   起点が業種名のサイト（AI集客ラボ・補助金）は、業種を単体でラッコに聞くと患者・
   消費者の検索しか返らない。`kw_seeds.core`（例: 集客/MEO/AIO/SEO）を業種に掛けて聞く。
   `core` が無ければ `owns` の先頭4語を使うが、「クリニック llmo」のような組ができるので
   **業種起点のサイトは必ず `core` を書く**。

   入れない語: 担当領域語（owns）を含まない／他サイトの領域語／指名検索／既存記事と
   食い合う／**求人・副業・資格・儲かる**（ラッコのLSIは重要度highで返すが読者は顧客でない）。
   語順・助詞が違うだけの語は同じ検索とみなす。

   **ラッコの上限（2026-10-08 運用者の決定。超えるなら呼ばない＝ハードストップ）**: 自動課金（オートチャージ）なので
   尽きて止まることが無く、警告では請求が止まらない。上限はすべて `scripts/rakko.py` の `allow()` が1か所で守る。
   | 上限 | 値 | 変え方 |
   |:--|:--|:--|
   | 1サイト・1か月 | **150** | `sites/<id>.json` の `rakko_monthly_cap` |
   | 全体・1か月 | **600**（4社分） | `rakko.TOTAL_CAP` |
   | 1回 | **150**（1サイトの月より大きい1回は意味が無い） | `rakko.RUN_CAP`（`kw_plan.CREDIT_CAP` も同じ値） |
   | 1サイトの150の内訳（目的ごとの枠） | 上位ページの見出し・共起語 **70**／実際の質問 **30**／候補の一括検索数 **30**／季節の推移・予備 **20** | `sites/<id>.json` の `rakko_budget`（例 `{"qa": 40}`。社の上限だけ変えた社は同じ比で伸び縮み） |

   - 課金の前に必ず見積もり（`RAKKO_EST`・目的ごと）を出し、**社の今月＋見積もりが社の上限を、全体の今月＋見積もりが
     全体の上限を、見積もりが1回の上限を超えるならラッコを呼ばない**（`RAKKO_GUARD=site_cap|total_cap|run_cap`）。
     **目的ごとの枠を超える目的だけ外して**、他の目的は続ける（`RAKKO_BUCKET=skip:<目的>`・`RAKKO_GUARD=bucket`）。
     止めた回は無料の材料（サジェスト・Search Console・控え）だけで組み、台帳は足すだけにして在庫を取り下げない
   - 許可（`allow`）が出た後も、`call()` が呼び出しごとに残りの枠（社・全体・1回・目的）を見て、**見積もりが外れても枠を超える呼び出しはしない**。
     許可の無い工程・計画に無い目的・**単価の資料が無い機能**（`rakko.PRICE` に無い経路）では呼ばない。単価は公式の資料
     （https://api.rakkokeyword.com/docs）で確かめ、**呼んで確かめない**
   - ラッコへの通信の口は `rakko.call()` の1か所だけ（門 `gates_history_h67` が確かめる）。使う工程は毎日の在庫の見張りの `kw_plan`
     （未着手が1か月分を切った社だけ・1か月1回。門 `gates_history_h71`）と、新しいお客様の登録のときの `kw_plan --site <id>` だけ。
     **週次の `kw_discover` は呼ばない**（控えにある応答だけを使う）。`kw_serp` は取った見出し・共起語・質問を残して読むだけ
   - 単価（公式の資料 v1.21.0・2026-10-09 に1経路1回だけ本物で確かめた）: 見出し 3／共起語 3／実際の質問 1.5／サジェスト・関連語 1.5／
     LSI・PAA 22.5／一括調査 1語0.03（1回最低15）
   - 見積もりは実際以上に出す（単価は公式の資料のまま・`--deep` の LSI/PAA 1起点22.5・一括調査の登録のやり直し1回ぶん）。
     2026-10-08 の お客様の社は実際 121回・195 に対し見積もり 210
   - **数え方（手元とCIで同じ合計）**: 1回ごとに `data/rakko_spend.jsonl` へ社・環境・目的つきで書き、管制塔の「ラッコ利用」タブ
     （`rakko_usage` / `rakko_log`）へ差分を写す。判断は「この環境の記録」と「管制塔の合計」の大きい方。**CI は管制塔に届かないとき呼ばない**。
     社を書く前の行（2026-10-08 より前）は全体の合計にだけ数え、推定で社に割り振らない。ラッコの API は残高（`GET /v1/account/info`・
     消費なし）を返すが、使用量・履歴を返す口は無い
   - `python scripts/rakko.py --check` が社ごとの今月の消費・上限・目的ごとの枠・止めた回数・残高を出し、止めた回・上限に達した社は
     週次の findings の「要対応」になる。月次のまとめ（`report_digest`）にも載る（お客様のPDFには載せない）
   - クレジットが尽きた場合（402）は打ち切って無料のサジェストで続け、記事作成は止まらない

   **ルール（必ず守る・仕組みで守る）: 課金の前に構成と正確性を固め、ラッコは最後に1回だけ使う。**
   試行錯誤の途中で本番のAPIを叩き直さない。実際に1日で約3,000クレジットを使った。
   **主因は一括調査の「SEO難易度」同時取得**（1語 +0.75。検索数の0.03と合わせて0.78、500語で 390）。
   検索数だけなら500語で15。難易度はサジェスト・関連語の応答に付いてくる分で足りるので、
   一括では取らない（`seoDifficulty: False`）。ラッコの単価は「機能ごと」ではなく「語ごと」に付くものがある。
   - 条件を直すときは `--dry-run`（課金なし）で構成を確かめてから本番を1回だけ回す
   - 毎日の見張りは dry-run（構成と目的ごとの見積もり）を先に記録してから本番に入る
   - 利用記録と応答の控えは Git に置かない（公開リポジトリ）。CI では GitHub のキャッシュで毎日の見張り・週次・月次をまたいで持ち越す。
     お客様の社の計画・上位ページの調べ・積んだ語の出どころは client_private の置き場（CI のキャッシュ）で執筆・書き直しへ渡す

   **定常運転（毎回クレジットを使わない）**:
   | いつ | 何を | 課金 |
   |:--|:--|:--|
   | 毎日（10:13・`daily-kpi.yml` の `kw-stock`） | `kw_plan --all --if-needed`（dry-run を先に記録） | **未着手が1か月分（1日の本数×30。本数を絞った社は絞った本数で）を切った社だけ・1社1か月1回**。月の途中でもその日に。1か月分×1.2 まで積み足す。1サイト月150・目的ごとの枠（見出し・共起語70／質問30／一括検索数30／予備20）まで |
   | 毎日（記事の枠の前） | `daily_audit` が8日分を切った社に `kw_discover`（無料） | **なし**（数日で尽きる社の当座の補充） |
   | 週次（月曜） | `kw_discover --append`（伸びている語の補充） | **なし**（ラッコは控えだけ。無料のサジェストと Search Console） |
   | 月次（1日） | 在庫は組まない（毎日の見張りと二重に組まないため、2026-10-09 に月次から外した） | — |
   | 新しいお客様の登録 | `kw_plan --site <id>` | 同上の上限 |
   | 常時 | `data/rakko_volume.json` の検索数を90日使い回す | 一括登録（最低15）を繰り返さない |

   **条件を直すときは取り直さない** — 応答は `data/rakko_cache/` に残っているので、フィルタの調整は課金なしで何度でもできる。
   実際、これをせずに1日で約1,200クレジットを使った。

   `--replace`（手で使う一新）は非破壊: 「未着手」を「対象外」に変えるだけで、公開済み・執筆中は触らず、
   行も消さない。優先度A/B/Cは並びの上位1/3ずつで、管制塔の `next_kw` はこの順に返す。
   週次の `kw_discover` は、この計画を土台に「伸びている語」を毎週足していく。

0. **食い合い審査（最初に実行・必須）**
   ```bash
   python scripts/kw_guard.py "<KW>" --site <site_id>
   ```
   終了コードで機械的に判定する。**LLMの目視判断で代替しない。**
   | 終了コード | 判定 | やること |
   |:--|:--|:--|
   | 0 | 着手可 | Phase 2 へ進む |
   | 1 | 要差別化 | 切り口をずらす。ずらせないなら次のKWへ |
   | 2 | **着手禁止** | 新規で書かない。既存記事を書き足す（リライト扱い） |

   検査するのは3つ。**タイトルの似かただけを見ても防げない**（実際、タイトル類似80%のゲートを通ったのに、狙う範囲が8記事と重なって51語・表示484回でクリック0になった記事がある）。
   - 既存記事の `keyword:` と表記ゆれを吸収した一致（「aio 診断」＝「aio診断」）
   - **GSCの実績**: その語で既に順位を持つ自社ページの有無（最も確かな指標）
   - 主題の重なり（参考値。文章の似かたは弱い指標のため止めない）

   管制塔側でも同じ検査が働く。`add_kw` は表記ゆれを吸収して重複を弾き、`claim_kw`（執筆開始）は同じ語が台帳にあると失敗する。**3サイト共通の台帳なので、他サイトが持つ語も弾かれる。**

   **担当領域の外の語も着手禁止（2）になる**（`scripts/kw_fit.py`。2026-10-08 に運用者が「GSC と GA4 に全く関係ない語が出ている」と指摘し、
   コーポレートの表示の約4割が銀行の通帳・ゆうちょの記事だった）。台帳へ積む（`add_kw`）・次に書く語を選ぶ（`next_kw`）・
   書いた後（`kw_gate --after`・`publish_flow`）も同じ判定を通る。同じ字で別の意味の担当領域語（「記帳」と通帳の記帳、「申請」と開業届）は
   `sites/<id>.json` の `kw_needs`（その意味を示す語）、担当の外の文脈は `kw_off` に書く。台帳に残った語は `python scripts/kw_fit.py --ledger` で一覧にする（`--retire` は運用者が確かめてから）。
   **新しく書く語だけの決まり**は `kw_require`（どれか1つに当たる語だけ新しく書く。`kw_fit.judge_new`）。AI集客ラボは 2026-10-19 から「業種」か「依頼する人の語」を含む語だけ（一般の AIO・LLMO の語は表示の約6割なのにクリック率0.22%だった）。既存の記事の書き直し・配信には効かない。

   **公開済みの担当領域の外の記事は、消さずに検索から外す**（`scripts/noindex.py`。2026-10-08 運用者の決定で26本）。フロントマターに
   `noindex: true`・`noindex_reason`・`noindex_date` を書くと、4つの描き方（build.py・nextjs-json・external-html・external-md）で
   head が noindex,follow になり、sitemap・llms.txt・一覧・関連・まとめのページから外れ、他の記事からのリンクは文を残して記法だけ外れる。
   週次の自動の直しは触らない。URL は 404 にしない（張られたリンクと評価を残す）。門: `tests/gates_history_h68.py`。

1. **記事作成ログの確認**
   - 「記事作成ログ」タブのステータス「未着手」の一番上の行を取得
   - 未着手行あり → そのKWで Phase 2 へ（Ahrefsリサーチ不要）
   - なし → 以下でKW選定を実行
2. **競合KW抽出（3C分析）**
   - Ahrefs `site-explorer-organic-competitors` で競合を自動発見
   - 競合3-5サイトの `site-explorer-organic-keywords` でKW抽出
   - フィルター: country=JP, volume>=200, position<=20
   - 自社の強み（Company）で独自価値を出せるKWを優先
3. **KWデータ取得**
   - `keywords-explorer-overview` で Volume / KD / CPC / Intent 取得
   - select: keyword, volume, difficulty, cpc, traffic_potential, intents / country: JP
4. **AI Overview表示状況チェック【AIO対応】**
   - 候補KWごとに `serp-overview` でAI Overview表示クエリかを判定し「KW戦略」タブG列に記録
   - 判断ルール:
     - **表示あり** → オーガニックCTR低下を織り込む。Info系なら「引用獲得」を主目的に設計。CV遠のInfo系単独狙いは優先度を下げる
     - **表示なし**（Do/Buy・ローカル・YMYL等） → 従来SEOのCTRが維持されるためCV直結KWとして優先度を上げる
     - どちらも「AI Overviewに引用される+クリックでも選ばれる」二段構え前提でPhase 3に引き継ぐ
4.5. **「開かないと済まない語」かの確認【必須】**
   ```bash
   python scripts/kw_intent.py "<KW>"
   ```
   同じ順位でもクリック率は5倍違う。28日の実測で、AI集客ラボの記事は6〜10位でCTR 1.04%、
   補助金サポートは同じ帯で2.80%だった。差は順位ではなく検索語の性質にあった。

   | 判定 | 例 | 扱い |
   |:--|:--|:--|
   | 強 | 不採択理由 / 書き方 / 対象条件 / トラブル | そのまま書く |
   | 並 | 業種×手法の掛け合わせ | 書いてよい |
   | 弱 | 例文 / 診断 / とは / 一覧 | **開く理由を用意してから書く** |

   「弱」の語は、検索結果に答えが1つ出た時点で用が済む。実際「口コミ 返信 例文 医療」は
   8.5位で表示88回・クリック0だった。書く場合は、**検索結果に出せないもの**
   （違反になる例・失敗事例・自社の一次データ）をタイトルと冒頭に置き、
   Phase 3の構成事前審査でその箇所を明示すること。

5. **SEO Knowledge批判3周** — 以下の10観点で批判的レビューを3周:
   1. ロングテール優先（Vol 1,000以下）に沿っているか
   2. CV距離（Do/Buy優先）の分類は正しいか
   3. カニバリゼーションリスクはないか（parent_topic確認）
   4. KD値の信頼性（SERP上位のDRで検証）
   5. トピカルオーソリティ設計（クラスター先→ピラー後）
   6. 競合SERPでDR低サイトが勝てている実績はあるか
   7. 独自性・E-E-A-Tを出せるKWか
   8. 攻め順序は妥当か
   9. 抜けているKWカテゴリはないか
   10. 【AIO】AI Overview表示クエリの場合、引用を獲れる独自ファクト・一次情報を用意できるKWか（「二重負け」KWになっていないか）
6. **KW確定・スプレッドシート更新**
   - 「KW戦略」タブに確定KW記録（G列: AI Overview表示状況含む）
   - 「記事作成ログ」タブに新行追加（ステータス: KW選定完了）

### Phase 2: リサーチエージェント

**目的**: 記事に独自性を持たせる一次情報（X投稿+YouTube文字起こし）を収集する。
**AIO観点**: 一次情報・独自データはAI検索が最も引用したがる素材。ここで集めた固有ファクトが「自サイトが引用される」決定打になる。

0. **収集の実行**: `python scripts/research.py "<KW>" --site <site_id>` を必ず先に実行する。
   YouTubeの文字起こしと自社の一次情報がまとめて出る（YouTubeはAPIキー不要）。
   保存された `data/youtube_transcripts/*.txt` を**執筆前に読む**こと。
   自動字幕は誤変換があるため、数値・固有名詞をそのまま引き写さない。

1. **X（Twitter）は使わない**。検索APIがBasicプラン（月100ドル〜）以上で、
   YouTubeの字幕から同等以上の一次情報が無料で取れるため見合わない。収集コードも削除済み。
2. **YouTube一次情報の収集**
   - YouTube Data API v3で関連動画上位10本を検索
   - `yt-dlp --write-auto-sub --sub-lang ja --skip-download -o "data/youtube_transcripts/%(id)s" "VIDEO_URL"`
   - 文字起こしを `data/youtube_transcripts/{videoId}.txt` に保存し「YouTube一次情報」タブに記録
   - **`python scripts/yt_quotes.py "<KW>"` で引用できる一文だけを抜き出す**。
     数万字の字幕をそのまま読んでも執筆に使われない（実際、字幕12本に対し引用0本だった）。
     数字を含む発言・体験・つまずきの3種に分けて出るので、そこから選んで本文へ組み込む
3. **数値ファクトの抽出【AIO対応】**
   - 「数値で語れるファクト」を3つ以上抽出してメモ化（例:「導入企業のN%が〜」）
   - AIは数値付き断定文を優先的に引用するため、Phase 4で出典付きで配置
4. **API 503エラー時**: 即フォールバックせず10分間隔でポーリング。3回連続503のみエラーログに記録して次工程へ
5. **記事作成ログ更新**: ステータス「一次情報収集完了」

### Phase 3: 設計エージェント（最重要Phase）

**目的**: 検索上位記事の構造分析→共通パターン+独自パートで構成確定。AI Overviewに引用されやすい「回答抽出可能な構造」を織り込む。

1. **検索上位10記事のH2/H3構造抽出**
   - `serp-overview` で上位10記事のURL / DR / タイトル取得
   - 全10サイト（最低7サイト）をフェッチしH2/H3抽出、スプレッドシートに書き出す
2. **AI Overview引用元の分析【AIO対応】**
   - AI Overview表示KWの場合、引用されているURLを確認
   - 引用ページの共通構造を分析: 冒頭直接回答 / 定義ブロック / 比較テーブル / FAQ / リスト構造 / 鮮度表記
   - 「10位以内だが引用されていないページ」との構造差分を特定し、引用されている側の構造を採用
   - 非表示KWの場合は強調スニペット獲得ページの構造を代わりに分析
3. **共通パターン分析**
   - 全サイトのH2をカテゴリ分類し出現率を算出
   - **共通60-70%**: 出現率50%以上のH2は踏襲（検索意図の核心）
   - **独自30-40%**: 出現率25%以下 or 0%のH2を一次情報から設計（差別化）
4. **Query Fan-Out設計【AIO対応】**
   - 共起語・サブトピックを10個設計し、本文で網羅する（トピック網羅性）
   - メインKWから派生するサブクエリを6-8個洗い出す
   - 各サブクエリに1つのH2が対応（1つのH2 = 1つの質問への完結した回答）
   - H2は「質問型」または「回答が予測できる名詞句型」（例:「◯◯とは？」「◯◯の選び方3ステップ」）
   - 各H2直下の「1文結論（40-60字の自己完結アンサー）」草案をこの時点で作成
5. **一次情報の配置確定**: 確定H2ごとに使うX/YouTube一次情報・数値ファクトを決定。メディア埋め込み可否も判断
6. **構成事前審査（執筆前ゲート・最重要）**: 以下の14項目を構成段階で自己審査し、**全項目○になるまで構成を修正してからPhase 4へ進む**。執筆後の修正ループより構成段階の修正のほうが圧倒的に安く確実なため、1項目でも×のまま執筆を開始することを禁止する。
   | # | 構成チェック項目 | 対応する採点観点 |
   |:--|:--|:--|
   | 1 | タイトル案が15〜45字・KW先頭・数字入り | SEO / 機械ゲート |
   | 2 | メタディスクリプション案が100〜160字（目安100〜150字）・検索意図に回答 | SEO / 機械ゲート |
   | 3 | **`kw_guard.py` を見出し案つきで再実行し、終了コード0**（下記） | カニバリゲート |
   | 4 | H2が6〜8個で、各H2がQuery Fan-Outのサブクエリに対応（質問型/名詞句型） | AIO |
   | 5 | 全H2に1文結論草案（40〜60字・単体で意味が通る）を書き終えている | AIO / SEO |
   | 6 | 冒頭200字の断言型回答の草案がある | AIO |
   | 7 | 定義ブロック・比較テーブル・FAQ 5問の配置場所が決まっている | AIO / デザイン |

     ```bash
       --title "<タイトル案>" --h2 "<H2案1>" --h2 "<H2案2>" ...
     ```
     Phase 1では語だけを見た。ここでは**見出し案を1本ずつGSCの実績に当てる**。
     タイトルと狙う語を差別化しても、見出しが既存記事の主題まで伸びていればそこで食い合う。
     「見出しの主題を既存ページが取っている」と出た見出しは、**削るか、要約1〜2段落にとどめて本文はそのページへリンクする**（ピラー記事の正しい形）。
     終了コード1以上のまま執筆を開始することを禁止する。
7. **ユーザー確認**: 確定H2構成（+1文結論草案）を提示し承認を得てからPhase 4へ。自動実行モードはスキップ可
8. **記事作成ログ更新**: ステータス「記事設計完了」

### Phase 4: 執筆エージェント

**目的**: 人間に読みやすく、AIが正確に抽出・引用できる本文を生成する。

1. **80%ドラフト生成**
   - 確定H2構成に沿って生成。一次情報を自然に組み込む（全体の20%以上）
   - 独自ファクト3箇所以上（数値ファクト優先）
   - **文字数は検索意図で決める**。フロントマターの `depth:` を必ず設定する
     - `quick`（3,000字〜）: 手順・定義・単一の疑問への回答
     - `standard`（5,000字〜）: 比較検討・選び方（既定）
     - `deep`（8,000字〜）: 網羅的なガイド・ピラー記事
     全記事が同じ長さに揃うと、それ自体が量産の指紋になる。上限は設けない
2. **AIO対応ライティング【必須実装】**
   - **冒頭200字の断言型直接回答**: 「◯◯は◯◯です」で書き始める。前置き・挨拶・一般論禁止
   - **各H2直下の1文結論**: 40-60字。その1文だけ切り出しても意味が通ること
   - **定義ブロック**: 「◯◯とは」を1-2文で明示、太字/枠囲みで視覚化
   - **ファクトと意見の分離**: 事実と体験談を同じ文に混ぜない
   - **情報鮮度の明示**: 冒頭付近に「2026年◯月時点の情報です」。変わりやすい情報には個別に時点を添える
   - **対象読者の限定文言**: 「この記事は◯◯向けです」を冒頭ボックス付近に明記
   - **代名詞の抑制**: 「これ」「それ」多用禁止。切り出し1文単体で主語が分かる書き方
3. **AI感排除チェック（7項目）** — 第6章の表を必ず全チェック
4. **文章ルール** — 第6章参照（ですます調 / 1文50字以下 / 段落3行以内 / 文長バリエーション / 体言止め2-3箇所 / H2直後の1行目は1文結論）
5. **X引用スタイル**
   - 一人称の体験は、登録した体験（`data/experiences.json`・お客様の社は非公開の `experiences.json`）からだけ書く。無ければ当社の判断とその理由を一人称で書き、そのあとで「〜氏も同様のことを言っています」と軽くリンク
   - blockquote禁止。インラインで自然に組み込む
   - `@username` は `<a href="https://x.com/username" target="_blank" rel="noopener">@username</a>` 形式
6. **SEO Knowledge品質批判10-20周**: 検索意図整合 / E-E-A-T / 内部リンク候補 / 独自性 / 読者が行動できるか / 【AIO】各H2が単体で「質問→完結した回答」になっているか
7. **記事作成ログ更新**: ステータス「執筆完了」

### Phase 5: 品質エージェント

**目的**: SEO+AIO最適化と多角的品質チェックで基準スコア達成。

1. **メタ情報設定**: タイトル15〜45字・KW先頭・数字含む（【2026年最新】のような飾りの年号は入れない。`score_check` が止める）/ メタディスク100〜160字（目安100〜150字）/ 冒頭にKW含む太字結論文
2. **E-E-A-T注入**: 著者情報（運営者名・肩書き・実績）/ データ引用（Ahrefs・公的統計・権威ソース）/ 自社事例。経験は登録した体験（`data/experiences.json`・お客様の社は非公開の `experiences.json`）からだけ書く。無ければ当社の判断とその理由を一人称で書く（「◯年の実務経験から」のような出どころの無い文を作らない）
3. **内部リンク・外部リンク**: クラスター内内部リンク3-5本 / 外部権威リンク3-5本 / アンカーテキスト「こちら」禁止（具体表現）
   - **リンク先は公開済み（score 90以上）の記事のみ**。未公開・審査中の記事URLをリンク候補に含めない
   - 保険として build.py が未公開記事へのリンクを自動テキスト化する（リンク先の公開後、再ビルドで自動復活）。隔離記事の生成HTMLも自動削除されるため、連鎖隔離は発生しない
4. **AIO/LLMO/GEO構造対応**: 冒頭200字断言回答 / 各H2冒頭1文結論 / 定義ブロック→数値ファクト3箇所（出典付き）→比較テーブル→Q&A / Query Fan-Out対応H2構成 / FAQ Schema 5問以上（回答40-60字・本文と完全一致）/ 鮮度表記とdateModified整合 / 失敗例・注意点セクション最低1箇所
5. **3観点の品質チェック（各100点。一次性80点以上・ほかの観点75点以上＋総合85点以上が公開条件・目標90点）** — 基準は `scripts/rubric.py`:

   **今の運用（2026-10-20 運用者の決定「公開前に、書いたAIとは別の工程で3観点を採点し、基準未満なら公開を止める」
   「書かない選択肢はない。1度や2度で完璧にするように」）**: 記事を書く AI は自分で採点せず、点数（`score`・`score_breakdown`・
   `quality_` で始まる項目）を書かない（書いた本人の点数は372本すべてが90点以上になり、門として働かなかった）。
   `score_check` を全PASSにして `publish_flow --check`（点数以外の門）を通したら終える。その後、鍵を外したままの機械の手順
   `scripts/quality_loop.py --new` が別の claude（読むだけ・一時フォルダの写し）で3観点を採点し、各軸に本文の引用が無い採点は捨てる。
   基準の近く（平均88〜93・1軸78〜84）は2回採点して軸ごとに低い方を使う。届けば機械が `score`・`score_breakdown`・
   `quality_attempts` を書く。届かなければ点の低い軸を `auto_rewrite --kind quality_loop` の検算つきで直して採点し直す（1回の実行で2回まで）。
   それでも届かない記事は捨てずに `quality_state: improving` のまま公開を止め（`rubric.gate_why`）、次の回の `--pending` が新しい記事より
   先に直し続ける。直している記事が残っても、その回の新しい記事は書く（運用者「書かない選択肢はない」。記事の枠のジョブは120分）。直しに使えるのは登録済みの一次情報・登録した体験・集めてある調べ・記事と一次情報にある出典だけ（事実を作って点を上げない）。
   直しても一次性が80点に届かない記事は、足りないのが材料なので、何を教えてほしいかを `material_requests.json`（お客様の社は非公開の置き場、
   自社は `data/`）に残し、材料が増えるまで Claude で直さない（`material.py --requests`・2026-10-20 お客様の記事が一次性40点で2回とも変更なし）。
   お客様の社は、材料のある題を先に書く（`hub_client.next_kw`。ある題が尽きたら無い題も書く）。
   「材料のある題」は、題の中身の語（サービス名・探し方の語を除く）を全部、材料の同じ文の40字以内に含み、母数つきの数字がある文があること
   （`material.hits`。語の片方だけに当たる周辺の数字で数えて、主題の数字が無いまま一次性78点で止まった・2026-10-31）。
   依頼の質問は、主題そのものの数字・採点者が無いと言った数字・見出しごとの実例を名指しで聞く（`material.questions`）。
   **材料が届かない題でも、当社調べを一次情報にする**（`own_survey.py`。2026-10-20 運用者「情報がなくても90以上になるように」）:
   記事の狙う語を Claude（Claude Code）・ChatGPT（契約の Codex）・Gemini（無料の枠の内）に聞き（従量課金の API は使わない）、見出しの論点の語・費用や期間などの
   観点が答えに出たか、出典の種類を数えて「当社が◯年◯月に3つのAIへ聞いたところ…」の文にする（数えたことだけ・解釈は書かない）。
   採点の工程は鍵を外して動くので、CI では鍵のある機械の手順として採点の前に測る（同じ月は聞き直さない）。直しの材料と増えてよい数字に入る。
   **抽出性と決定支援は書く段階で機械が止める**（`score_check`）: H2直下の1文を「これ」「その」「◯つのうち」「起きるのは」「理由は」で
   始めない／「◯◯なら A」の分かれ目2つ以上・やらない判断・「まず◯◯してください」の一歩。直しの指示にも機械の指摘として渡す。
   **点の低い公開済みの記事は、公開前の採点で合格が出てから毎日の記事の枠で1本ずつ直す**（`quality_loop --rescore-auto 1`。
   運用者「これで90点以上であれば評価が低い記事を修正していって」2026-10-20）。始める条件は直近14日の公開前の採点で合格3本以上・50%以上。
   一気に直さない: 社ごとに7日で12本まで／よく読まれている記事（10位以内でクリックあり）は後回し／対照群（月ごとに5本に1本）は触らない
   （効果を比べる相手を残す）／当社調べは1記事2文まで・書き出しは記事ごとに3通りに散らす（同じ一文が並ぶと量産の指紋になる）。
   公開済みの記事は週次の `--rescore`（社ごとに4本）が採点し、届かなければ公開したまま直す（取り下げない）。記録は `data/quality_loop.jsonl`
   （お客様の行は非公開の置き場）。週次の `score_audit.py` は公開後の抜き取りとして残す。
   下の採点プロトコルは、3観点で採点する工程（quality_loop・score_audit・人の採点）が守る決まり。

   **採点プロトコル（甘さ・ブレを防ぐ実施ルール）**:
   1. **機械採点を先に**: `python scripts/score_check.py <slug>` を実行し、数えられる18項目（文字数・マーカー・FAQ・リンク・H2構造・AI感NGワード等）を**全PASSにしてから**LLM採点に入る。機械で測れる項目をLLMに採点させない
   2. **初見の読者として読む**: 採点時は執筆の経緯を忘れ、公開HTMLを初めて読む読者・審査員の視点で本文だけを評価する
   3. **批判先出し**: 各エージェントは採点前に必ず「この記事の欠点・改善点を3つ以上」列挙してから点数をつける（欠点ゼロの採点は無効とし、やり直す）
   4. **足切り**: 総合85点以上でも、**一次性が80点未満、またはほかの観点が75点未満なら不合格**（1観点の壊滅を総合点で覆い隠さない）。総合は3観点の**平均**
   5. **内訳の記録**: 3観点で採点した場合は、フロントマターに `score:`（3観点の平均）と `score_breakdown:`（3観点の素点）の両方を記録する。
      内訳がある記事は、門（`rubric.gate_why`）が平均を計算し直し、書かれた `score` と低い方で判定する。観点の欠け・数字でない値は不合格
      ```yaml
      score: 93
      score_breakdown: {originality: 94, extractability: 92, decision: 93}
      ```


   **採点する3観点（各100点・基準は `scripts/rubric.py` に1か所だけ置く）**:

   | 観点 | 何を見るか | なぜ見るか |
   |:--|:--|:--|
   | **一次性** | そこにしか無い情報があるか | AIが回答の根拠に選ぶのは、他所に無い数字と経験。まとめ直しは、どれだけ整っていても引用されない |
   | **抽出性** | AIが答えとして切り出せる単位か | AI検索は本文を段落単位で切り出す。その1つを取り出して意味が通らなければ引用されない |
   | **決定支援** | 読者が次の行動を決められるか | 読んで終わる記事は、順位が取れても問い合わせにならない |

   各観点に**本文からの引用を1つ**必ず書かせる。引用の無い点数は採点ではなく感想。
   目安の点数（100/80/60/40/20点の記述）は `rubric.py` の `AXES` を参照する。

   **機械で数えられることは、ここで採点しない**（文字数・見出しの数・リンクの本数・
   FAQの個数・マーカー数は門2の `score_check` がすでに判定している）。
   二重に見ると、項目が多いだけで差の付かない採点になる。

   **修正ループ**:
   ```
   採点 → 総合 < 90点（目標）、またはいずれかの観点 < 80点の場合:
     1. 最低スコアのエージェントの指摘を優先確認
     2. 指摘事項を上から順に修正
     3. 修正したエージェントのみ再採点（他スコア維持）
     4. 各観点80点以上かつ総合90点以上になるまでループ（最大3サイクル）。85点以上に届いていれば、届かなくても最高点の版で公開する
     5. 3サイクル後も未達 → ユーザーに差分報告して手動判断
   ```
6. **記事作成ログ更新**: ステータス「品質チェック完了」（I列に「総合スコア/100」）

### Phase 6: 公開エージェント

**目的**: 画像生成→HTML生成（メタ+Schema直書き）→Cloudflare Pagesへデプロイ。

1. **アイキャッチ画像生成**: `python scripts/make_images.py <slug>` / 16:9 / カテゴリカラー準拠 / タイトルを自動折り返し・自動縮小 / `site/images/{slug}/` に配置
2. **H2直下の図解画像生成**（目安3-5枚）
   - イラストonlyの高品質フラットベクターイラスト
   - **英語テキスト禁止**: プロンプトに「No English text whatsoever. Japanese text only or no text at all.」必須
   - 生成後に目視チェック、英語混入は再生成。altテキスト必須
   - 【AIO】図解の重要情報は必ず本文テキストでも記述（AIは画像を引用できない）
3. **HTML生成（`scripts/build.py`）**
   - `articles/{slug}.md` → `site/{カテゴリ}/{slug}/index.html`（`templates/article.html` 適用）
   - Python `markdown` ライブラリ（extensions: tables, extra）で変換
   - 画像は `<figure>` + `<figcaption>`。見出し階層（H2→H3→H4）のネスト検証
   - 目次（TOC）をH2/H3から自動生成して冒頭に挿入
4. **メタ情報の直書き**（テンプレート変数で注入）
   - `<title>`: SEOタイトル（KW先頭・15〜45字）
   - `<meta name="description">`: 100〜160字（目安100〜150字）
   - `<link rel="canonical">` / OGP（og:title, og:description, og:image=アイキャッチ）
5. **JSON-LD Schema直書き【AIO対応】**（テンプレートに埋め込み）
   - BlogPosting: headline / author（Person: 名前・肩書き・プロフィールURL） / datePublished / **dateModified** / image
   - FAQPage: 本文FAQセクションと**完全一致**（不一致はスパム判定・AI不信頼リスク）。回答40-60字目安
   - BreadcrumbList: トップ > カテゴリ > 記事
   - HowTo: 手順系記事のみ追加（各ステップ1-2文）
6. **サイトメタファイル更新【AIO対応】**
   - `site/sitemap.xml` にURL追加（build.pyが再生成。lastmod=公開日）
   - `site/llms.txt` に `- [記事タイトル](公開URL): 記事の1行説明` を追記
   - トップページ・カテゴリ一覧ページに新着記事リンクを追加
7. **ローカル検証**
   - 生成HTMLをブラウザ確認（レイアウト崩れ・画像リンク切れ・TOC・CTA表示）
   - JSON-LDをリッチリザルトテスト相当の構文チェック（パースエラーなし）
8. **デプロイ（=公開）**
   ```bash
   git add site/ articles/ && git commit -m "publish: {記事タイトル}" && git push
   ```
   - Cloudflare Pages が自動ビルド・配信。数分後に公開URLを確認
   - 通常モード: commit後にユーザー確認→pushで公開。自動実行モードは足切り（一次性80・ほか75）と総合85点以上で自動push
9. **記事作成ログ更新**: ステータス「公開済み」

### Phase 7: 分析エージェント

**目的**: インデックス登録・AI検索向けURL通知・データ更新・内部リンク追加・AIO計測・KPIレポート。

1. **Google Indexing APIで即時インデックス登録**
   ```python
   from google.oauth2 import service_account
   from googleapiclient.discovery import build

   credentials = service_account.Credentials.from_service_account_file(
       'indexing-service-account.json',
       scopes=['https://www.googleapis.com/auth/indexing'])
   service = build('indexing', 'v3', credentials=credentials)
   service.urlNotifications().publish(
       body={'url': 'https://YOUR_DOMAIN.com/post-url/', 'type': 'URL_UPDATED'}).execute()
   ```
   未設定の場合: GSC URL検査ツールでの手動登録をユーザーに依頼
**通知は3サイトすべてに送る。** 以前は AI集客ラボ の sitemap しか見ておらず、コーポレートと
補助金は記事を出しても検索エンジンに知らせていなかった。実測で、公開から13日以内に一度でも
検索結果に出た割合が AI集客ラボ 72% に対しコーポレート 41% と差が出ていた（2026-09-22）。
IndexNow は**鍵ファイルが各ドメインの直下で配信されていること**が条件（置いただけでは足りない。
補助金サイトは `tools/make_dist.py` の配信対象に入っておらず、置いた鍵が配信されていなかった）。
**IndexNow へ送るのは、中身が変わった・新しいページだけ**（`notify_indexnow.py`。AI集客ラボは題・説明文・本文の印で比べ、
日付・CSS の版・関連記事の並びだけの変化は送らない。手元に HTML の無いサイトは同じURLを1日1回まで。送った印は
`data/indexnow_sent.json` を CI のキャッシュで持ち越す）。前は自社の枠のたびに sitemap の全URLを送っていた（2026-10-31）。
Ahrefs の IndexNow の指摘は、Ahrefs が巡回の間に中身の変化を見たページを「送る候補」として出す一覧
（Ahrefs のヘルプ。Ahrefs から自動で送る設定にすると出なくなる。他の経路で送った分を数えるかは書かれていない）。

2. **IndexNow送信【オプション】**
   ```bash
   curl "https://api.indexnow.org/indexnow?url=https://YOUR_DOMAIN.com/post-url/&key=${INDEXNOW_KEY}"
   ```
3. **AIO計測データの取得**
   - GSC生成AIパフォーマンスレポート: **APIから取れない**（2026-09時点）。`searchanalytics.query` の `type` は web/image/video/news/discover/googleNews のみで `aiOverview`・`aiMode` は無い。画面とCSVだけ、指標は**表示回数のみ**（クリック数は提供されない）。月1回、人がCSVを落として `python scripts/genai_import.py <csv> --site <id>` で取り込む

   - 「AIO計測」タブに新行追加
4. **スプレッドシート全タブ更新**: ダッシュボード / 記事作成ログ / KW戦略 / トピッククラスター / KPIレポート / AIO計測
5. **既存記事への内部リンク自動追加**
